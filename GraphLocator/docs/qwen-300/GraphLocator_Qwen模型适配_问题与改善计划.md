# GraphLocator + Qwen：定位问题、改善计划与预期结果

编写日期：2026-10-09（北京时间）  
状态：已获用户授权并实施；修复后七题金丝雀与90次开发对照均已完成，按预定函数F1主指标选择B2，统一冻结300题已完成（277完成、23超限失败），双报告与Excel已交付。最终冻结结果以新报告为准。

## 1. 目标与实施边界

继续使用现有本地 **Qwen2.5-Coder-7B-Instruct**，改善模型替换后出现的搜索、结构化输出和因果关联问题，使 GraphLocator 的两阶段流程能够更可靠地工作。优先恢复有效检索和代码关联，再验证实际定位效果是否提高。

本轮保留 RDFS 仓库图、搜索种子、邻居扩展、因果图和优先队列等核心机制。模型权重、温度 0、seed 0、65536 上下文及现有服务参数固定。不增加付费模型调用，不在主方案中引入函数功能说明、BM25 或 CoSIL 文件候选；这些若需要验证，另设实验条件。

现有 `GraphLocator/Qwen` 和 `CoSIL/on`、`CoSIL/off` 预测作为冻结对照。新方案称为 **GraphLocator/Qwen-适配v2**，属于保留核心机制的模型适配实验，不称为作者 GPT-4o 原配置的严格复现。提示词、输出协议、查询分页和异常恢复的差异均列入补丁及运行清单。

论文和日志支持“当前流程与 Qwen 的交互存在问题”，尚不能确定每项问题的独立贡献。下面分别记录事实、解释假设和拟议处理，不把模型规模直接当作已证实的原因。

## 2. 已确认的问题与基线

| 问题 | 已观察到的证据 | 当前判断与影响 |
|---|---|---|

| 金丝雀检查不充分 | 旧准入检查响应、搜索和因果解析调用是否发生 | 验证了流程执行，未充分验证输出内容与代码关联是否可靠 |

## 3. 改善方案

### 3.1 搜索工具与上下文控制

涉及 [搜索工具](../../utils/execute_search.py)、[搜索 agent](../../search_agent.py)、[工具提示词](../../prompts/search_agent_prompt.py)及 [模型适配层](../../llms/__init__.py)。

1. 工具描述、实际节点/边类型、参数枚举及示例统一，检查类似 `UseBy` 与 `UsedBy` 的名称差异。参数缺失、非法枚举和双通配符明确反馈，不执行猜测后的查询。
2. 区分精确匹配、名称模糊匹配和通配匹配。单独 `*` 继续表示任意值；内嵌 `*` 明确定义为名称模式匹配，不再被误送入编辑距离排序。该行为变化单独记录，不能称为完全等价的部署修复。
3. 模糊检索保留 `top_k=5`。广泛节点查询和边查询使用稳定顺序、去重、分页和 token 预算，不把所有源码一次交给模型，也不任意取图插入顺序的前五项冒充相关性排序。记录总匹配数、返回 ID、已处理分页及未处理数量；分页内部处理与 agent 搜索轮数分别计数。
4. 分批提供完整节点源码。初始开发参数为每批最多 8 个节点、相关性输入预算约 12k token、因果输入预算约 48k token，最终以真实 tokenizer 的剩余容量为准。超大单节点独立处理，仍放不下则记录明确的预算失败，不静默截掉函数主体。
5. 分词超时初始调为 120 秒，最多重试一次；推理传输仍使用显式、有日志的重试。完整请求或请求摘要在分词预检前留档，区分分词失败、上下文拒绝和模型请求失败。

这些参数是开发起点，尚非实测最优值。限制检索规模可能损失召回，因此需同时检查候选覆盖和未处理分页，不能仅以不再超限作为成功标准。

### 3.2 相关性判断改为带 ID 的结构化输出

将无编号的 True/False 长列表改为节点 ID 与布尔判定的集合。主方案保留原来的相关性判断目标，先隔离输出格式的影响；放宽为“症状或背景上下文相关”属于筛选策略变化，另设消融。

- 每个待判断节点使用唯一 ID；输出包含 `node_id` 和 `is_relevant`，不要求生成长篇解释。
- 检查 ID 是否来自该批、是否重复冲突、是否缺失，以及值是否为布尔类型。禁止按返回行号错位对齐。
- 已合法完成的判断保留；只针对缺失或冲突项进行最多一次格式纠正。仍未解决的项标记为 `unknown`，不把 unknown 默认为 True 或 False，也不丢掉同批其他合法结果。
- 若现有服务支持结构化输出约束，先用独立检查验证后启用；否则使用 JSON 请求加本地 schema 校验，不假定服务一定支持。
- 保存原始回答、有效项、无效项、纠正请求及最后未解决项，统计首次有效率和纠正后的覆盖率。

预期减少由格式、数量和输出截断造成的整批候选损失；仍可能存在合法格式下的错误相关性判断。

### 3.3 因果输出简化与稳定代码关联

涉及 [因果提示词](../../prompts/causal_agent_prompt.py)与 [因果 agent](../../causal_agent.py)。

1. 去掉“递归检查、交换因子、Product 依赖”等带具体问题含义的示例，改为字段说明。要求每个因子的描述对应当前 issue，并给出简短源码依据；允许证据不足，不要求为凑格式虚构原因。
2. 输入改成清晰的对象列表，列出稳定代码 ID、文件、限定名称、行号及源码，避免 Python 字符串列表的多层转义。代码 ID 由 base commit、路径、节点类型、限定名称和位置稳定生成，不依赖当前批次的 1/2/3 编号。
3. 模型输出因子、代码 ID 和带概率的因果边；程序校验后构建 CIG，再渲染 Mermaid 供报告展示。仍保留每个因子最多关联一个代码节点、邻居扩展和优先队列，不以 JSON 输出替代因果推理。
4. 现有因子更新采用显式操作：保留关联、替换关联或撤销关联。未提及的关联维持原状态；只有可追溯到已展示源码的 ID 才能新增或替换。概率限制在 [0,1]，不存在的因子/边端点和错误 ID 不进入有效图。
5. 初始和更新请求统一任务约束，保留现有 CIG 与必要源码上下文。格式错误最多纠正一次，不通过增加无上限的重试弥补。
6. 证据文本能检查出处，但不能自动证明原因正确。单独审查“输出合法但解释与 issue 不符”的情况，避免只检查 JSON 是否可解析。

稳定 ID 和 JSON 均是 Qwen 适配行为。旧模型的原始 Mermaid 回答不重新解释后覆盖旧预测；新旧协议各自留档并对照。

### 3.4 停止、空结果与预算

保留搜索 `max_search_turn=5` 和因果 `max_turn=20` 的参数。旧实现实际允许最多 21 次因果更新，新方案先按同样的实际更新上限对齐，避免同时引入停止条件变化；格式纠正、子批次判别、分页和传输重试均单独统计实际调用次数。

空种子、空因果图、所有关联无效、预算不足、模型主动结束、运行异常采用不同原因码。正常搜索后确实没有依据可以返回空结果，不强制生成函数或种子。出现空图时不在无候选情况下反复请求模型猜测定位。

**主方案不增加空种子回退检索。** 若以上适配后空种子仍然严重，再单独评估 issue 符号/报错位置检索或 BM25 回退，命名为 `GraphLocator/Qwen-适配v2+回退检索`，与主方案分别报告。

## 4. 实验步骤与对照

### 4.1 冻结输入与版本

以相同 SWE-bench Lite 300 个 issue ID、repo、base commit 和 issue 文本为输入，按 ID 对齐 CoSIL。真值仅用于离线评价；修复 patch、测试 patch、真值路径和正确函数不进入模型提示词。

存档旧代码快照、模型配置、提示词、数据哈希、预测及评分。新运行使用独立目录 `results/qwen_adapt_v2/`，不复用旧 canary gate，也不将旧成功题直接混入新版本结果。

### 4.2 离线检查与金丝雀

先验证真实已暴露的故障：超大查询、闭合格式缺失、重复/缺失 ID、0/负/越界 ID、已有因子关联更新、工具历史顺序、空种子和空图。检查有效历史输入在转换后没有代码实体错位。

金丝雀包含旧三题 `astropy__astropy-12907`、`django__django-11848`、`sympy__sympy-12481`，并加入从故障类别确定的边界案例。案例名单与检查项在运行前固定，不按新版本是否命中选择题目。

准入要求：工具可有效执行；合法 ID 不错位；相关性缺项被显式处理；因果更新关联可追溯；每个输出函数能审计实际请求中的源码来源；没有未处理的协议异常。逐题核对问题描述、源码依据与原因是否明显不符，保留原文和判定；不能把模型自称“分析正确”当作内容检查证据。

准入不要求 benchmark 真值命中，不以“模型响应过、parse 被调用过”作为唯一条件。适配后语法合法也不代表定位正确。

### 4.3 30 题开发与分项对照

开发集约 30 题，按项目和已有运行故障类别确定，包含金丝雀；选题不使用新方案的命中结果。保存选题规则、固定种子及 issue ID 清单。

| 条件 | 内容 | 用途 |
|---|---|---|
| B0：历史 GraphLocator/Qwen | 已冻结预测和日志 | 原始参照，无须重新生成旧预测 |
| B1：基础恢复 | 分词/传输修复、查询说明与分页预算、完整审计 | 观察运行与检索改善；细分各项行为差异 |
| B2：相关性输出适配 | B1 + 带 ID 的结构化判别与有限纠正 | 观察候选是否因格式损失而改善 |
| B3：因果输出适配 | B2 + 中性提示、稳定 ID、结构化因果更新 | 观察因果内容和关联可靠性 |

只在开发集做逐步对照，先定位改善发生在哪里。结果不支持某项改动时，报告失败或退化并决定是否保留，不能只展示最好的一次输出。若同时修改多项且缺少独立消融，不给出单项因果贡献结论。

### 4.4 冻结适配版本后的验证

冻结最终代码、参数、提示词和输出协议，对其余约 270 题验证；验证期不继续按题调参。该部分称为“未参与本轮适配调试的验证集”，由于本批题目的历史总体诊断已被参考，不宣称全新、从未观察过的独立 benchmark。

最终需要全量报告时，用冻结版本重新执行开发题，形成同版本 300 题结果，同时单独列开发集与验证集成绩。以验证集上的同题新旧差异作为主要效果证据；300 题汇总用于完整记录和历史表格兼容。B0 与新版本必须在同一子集、同一适用分母上比较，不能用新版本 270 题的 F1 与旧版 300 题的 6.10% 直接比较。总览保留实际失败和空预测，不靠反复重跑后挑最好结果。只对明确的部署/传输故障作预先规定的恢复，保留所有尝试及最终取值规则。

只使用运行前核实空闲的 GPU，不停止其他进程。先以现有服务或空闲副本完成金丝雀，再按负载扩展；副本权重、启动参数和模型请求一致性留档。

## 5. 评分与跨实验比较

参考 [论文 4.2 节](https://arxiv.org/html/2512.22469v1#S4.SS2)，主报告采用逐题集合的 Precision、Recall、F1 和 SL，函数级为重点，同时报告文件与模块级。每题先计算指标再取宏平均，F1 不由全局平均 P、R 二次计算。

- Precision：该题正确预测数 / 去重预测数。
- Recall：该题正确预测数 / 真值目标数。
- F1：2 × 正确预测数 /（预测数 + 真值数）。
- SL：是否覆盖该题全部真值目标。

两条轨道同时保留：

1. **论文复现轨道**：使用作者原生真值与完全限定实体匹配，原生函数适用 277 题，旧/新版本都用相同规则；已知作者真值格式问题原样留档，不静默改正后称为原生分数。
2. **跨项目共同轨道**：使用 CoSIL 已验证真值，重新对所有项目采用一致的集合定义、函数身份匹配和去重规则计算 P/R/F1/SL。先审计类限定名称与不完整函数名的转换；多义名称不靠真值选择类。严格限定名匹配与既有末段名匹配若不同，分别命名报告，不能混合。共同真值的原有函数适用数为 293，若实体审计影响可评分集合则明确列出原因及新旧分母。

历史 Excel 的 Top-1/3/5 判定及已有列保持原样；GraphLocator 原输出无置信度排名，Top-k 作为历史兼容指标。新增集合指标使用独立汇总页/数据字段，不把排名指标伪装成论文指标。

运行失败和空预测在适用题目的指标中计 0；缺少结果单独标记并阻止声称完成全量；无该层级真值计 NA 并报告分母。函数、类、变量分别处理，类和变量不充当函数级正确预测。

## 6. 预期结果与验收方法

下面是待验证的工程目标和研究目标，不是已实现的结果，也不是准确率保证。

| 观察项 | 旧基线 | 初步目标与验收 |
|---|---:|---|
| 全量运行失败率 | 40/300，13.33% | 争取降至 5% 以下；按故障类别解释残留，不能靠删除失败题达标 |
| 完成题中的空种子率 | 160/260，61.54% | 争取降至 30% 以下；同时观察种子相关性与目标覆盖，不强制返回种子 |
| 相关性数量不匹配 | 31/209 次逻辑判别，14.83% | 明确对应全部候选 ID；比较纠正后的未解决比例，子批次与原逻辑判别分开统计 |
| 编号与实体关联 | 有无效编号及旧因子关联更新限制 | 最终采用的关联均合法且有来源；无静默错位，分别记录首次非法率与修复后未解决率 |
| 因果示例牵引 | 初始答复 264/269 出现示例标签 | 无关原因组合明显减少；结合 issue 匹配及源码依据审查，不能仅因删除示例后旧标签消失就判定成功 |
| 目标进入因果候选 | 44/293，15.02% | 期望增加；如果覆盖没有改善，需解释后续选择改进的上限 |
| 作者原生函数 F1 | 6.10% | 期望提高，数值待实测；同步报告 P/R/SL，不能只挑上升指标 |
| 共同函数 Top-5 | 8.53% | 作为兼容指标观察；不预先承诺达到 CoSIL/off 的 37.88% |

**提升幅度不能据现有日志可靠预测。** 如果仅在已观察到的候选中重新选择、不改变候选覆盖，44/293 的目标覆盖只提供约 15.02% 的理论覆盖上限，且不意味着这些题都能被选对。要获得更大的改善，搜索和邻居探索必须让更多目标进入真实模型请求。

较有依据的预期是：超时与格式导致的非正常失败减少，候选和关联更可追溯，输出重复减少；实际定位是否提升以及提升多少由冻结版本验证决定。提高 Recall 可能同时引入更多错误候选、降低 Precision，故以完整指标和逐题差异评估。

主方案以同口径新旧函数 F1 及配对逐题变化评估；报告宏平均指标、适用题数、置信区间或配对 bootstrap 区间。小样本结果用于调试，不据此声称统计上稳定优于 CoSIL。若语法可靠但准确率未提高，应继续分析搜索覆盖和原因判断，而不是重复生成后择优。
