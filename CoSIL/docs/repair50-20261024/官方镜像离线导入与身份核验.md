# 官方镜像离线导入与身份核验

本记录属于 repair50 的测试环境准备，不改变抽样顺序、模型配置、提示词或评分规则。

## 为什么准备另一条传输路径

共享 Docker 的只读 `docker info` 显示 `HTTPProxy` 和 `HTTPSProxy` 均未配置。客户端 shell 中存在批准的代理，不代表 Docker daemon 会使用该代理。首题原 daemon pull 长时间只有两条 `Pulling fs layer` 记录；这与网络路径差异一致，但仅凭这些事实不能确定底层网络失败原因或宣称零字节传输。

备用方法由资格执行器在终止本轮自己的原 pull 客户端后串行使用：用户态 crane 经已批准的代理下载同一个固定摘要的公共官方镜像，先验证归档，再通过 `docker load` 导入已有 daemon。没有修改共享 daemon、启动特权容器、切换任务或跳过大镜像。

## 固定工具与来源

- 工具：[Google go-containerregistry/crane v0.22.1](https://github.com/google/go-containerregistry/releases/tag/v0.22.1)。
- 官方 Linux x86_64 release archive：16,496,784 字节；SHA256 `0ab7a1d6932a213aed964ce97666c3077fe691c8606413674a8b3e0b9ec4cda0`。
- 从校验后的归档只提取 `crane` 可执行文件；可执行文件 SHA256 `8e75c326adb43b053cfd78b9b987663f8f4fe4557f4d3915905643f25c730992`，每次启动前再次核对。
- 用户态位置 `/tmp/repair50_20261024/tools/crane-v0.22.1/`；不会安装到系统目录。
- [固定版本 pull 实现](https://github.com/google/go-containerregistry/blob/v0.22.1/cmd/crane/cmd/pull.go)及[归档写入实现](https://github.com/google/go-containerregistry/blob/v0.22.1/pkg/v1/tarball/write.go)。

下载子进程使用单独的空 Docker `auths` 配置，不读取用户 Docker 凭据，不继承 DeepSeek API 密钥。仅该子进程省略 `NO_PROXY`，使公开注册表与重定向的层文件走已有批准代理；不修改 shell 或主机配置。

## 身份证明链

`code_repair50/image_transport.py` 采用以下校验：

1. 只接受 `swerebench/...@sha256:...`；从原公开 manifest 回执重新验证原始 manifest 摘要。
2. 不提取第三方归档路径。归档只允许一个镜像、一个 config 和原 manifest 指定的层，拒绝额外路径、非普通文件及重复成员。
3. config 的字节数和 SHA256 必须与原 manifest 一致；镜像必须是 Linux/amd64。
4. 各层压缩字节数、SHA256 及顺序必须与原 manifest 一致。流式 gzip 解压计算真实未压缩 SHA256，必须逐项等于 config 的 `rootfs.diff_ids`。
5. `docker load` 后分别识别旧版 config 摘要型 ID 和 containerd manifest 摘要型 ID。后者必须与原 manifest 的完整字节摘要，或 Docker29 描述符字段顺序重新序列化后的完整字节摘要精确一致，并与实际 `Descriptor.digest/size/mediaType` 一致；config 与各压缩层的所有描述符字段保持完全相同。`RootFS.Layers` 必须逐项等于已校验 diff IDs。正式容器使用实际核验出的不可变本地 image ID。

导入前还检查归档 `RepoTags`：若某个标签指向无法通过上述完整身份链验证的其他镜像，则拒绝导入，防止改变共享 daemon 中已有标签的指向。同一个 config 在 containerd 中显示为 manifest 型 ID，不应被错误判定为另一张镜像。无标签的归档不需要此类查询。

**归档导入不保证保留 `RepoDigests`。** 回执分别记录原 registry reference 与实际本地 image ID；不会将缺失的 RepoDigest 写成验证成功，也不会通过重新打官方摘要标签伪装这一点。

## 运行边界与回执

- 每次只进行一条完整下载路径。首题小 manifest 连通性核验实测 3.83 秒成功，没有下载任何镜像层；这一结果不等于完整镜像或正式测试已成功。
- 下载与导入期间每秒检查共享镜像所在盘剩余至少 10GiB、`/tmp` 至少 20GiB；触及门槛或预设超时仅终止本轮自己的客户端。
- 不启动容器，不调用模型，不修改 daemon 配置，不 prune 或删除其他镜像。资格执行器单独管理本轮镜像租约和容器。
- 首次完整下载、压缩和未压缩哈希核验、导入日志与本地身份回执分别保存。已验证的镜像仍存在时直接复用；本轮清理后可从同一归档重新导入，重新导入日志采用独立目录，保留原回执。
- 候选资格仍必须由正式 gold/base 测试确定。镜像传输故障属于系统阻塞，不能按镜像大小替换候选，更不能将其计作模型修复失败。

入口为 `ensure_verified_image(client, manifest_record, workdir=...)`，由资格执行器单路调用。相关 CPU 单元测试检查摘要篡改、层顺序、真实解压 diff ID、额外归档路径、缺失 RepoDigest、匿名凭据隔离及缓存复用；这些测试不代替真实镜像导入和正式测试。

## 有限 Range 吞吐探针

在首镜像原 crane 下载继续进行期间，对同一个公开层进行了不超过 16MiB 的小探针。请求全部返回严格正确的 HTTP206、Content-Range 和字节数。

| 小探针 | 有效载荷 | 耗时 | 吞吐 |
|---|---:|---:|---:|
| 四个 1MiB 段，单连接依次请求 | 4MiB | 17.59秒 | 0.227MiB/s |
| 四个 1MiB 段，四连接并行 | 4MiB | 5.69秒 | 0.703MiB/s |
| 四个约 1.984MiB 段，四连接并行 | 约7.94MiB | 6.46秒 | 1.229MiB/s |

探针累计有效载荷 16,711,680 字节，小于 16MiB。小段并行比同样小段串行快，但请求建立延迟占比很大，不能据此宣称整个镜像会获得同样倍数的提升。较大段探针的绝对吞吐没有明显超过同期持续 crane 下载的观察值，且探针与原下载共用网络，不能当作严格独立吞吐基准。

因此没有启动第二条完整镜像下载，也没有把并行 Range 下载加入正式执行路径。继续使用已核验的 crane 方案。原始探针回执为 `runtime_preflight/range_transport_probe.json` 和 `runtime_preflight/range_transport_probe_larger_segments.json`。

## Docker29 真实导入兼容修复

首镜像完整归档 1,852,805,632 字节，压缩层与实际解压 diff IDs 校验通过，`docker load` 也已成功。但旧身份检查把所有 Docker image ID 当成 config 摘要，随后查找 config ID 返回404，因此资格执行器按系统错误停止，没有启动测试容器或模型请求。

只读检查本轮镜像得到：

- 原 registry manifest：`sha256:81b801d64dc175ac0b5fbebe139af7b76134791a648f27356ff2e6af24172f59`。
- 原 config：`sha256:290bcc2d1f2fd187ba29f2d21a9281893f8f214ce02f3fef7b5ffc89e0aa00bc`。
- Docker29 实际本地 ID 及 `Descriptor.digest`：`sha256:1d7c6a2797e388785bb029fb4cf64d3b4e844be378bbf96ae9e6c7cc8e19f820`。
- crane 的实际归档带有 `index.docker.io/swerebench/sweb.eval.x86_64.tobymao_1776_sqlglot-4618:i-was-a-digest` 标签，并不是无标签归档；不能依赖“按digest拉取就没有RepoTags”的假设。

通过只读 `docker image save` 流，仅保存590字节本地 manifest 和2651字节原始 config。二者实际 SHA256 分别严格等于本地 ID 和原 config 摘要。本地 manifest 与原 manifest 解析后完全相等，仅描述符 JSON 字段顺序不同：Docker29 的顺序为 `mediaType,digest,size`。原配置、压缩层字节及层顺序都没有变化。Docker/containerd 的 manifest 型 ID 行为也可见于[Moby 官方实现](https://github.com/moby/moby/blob/master/daemon/containerd/image_inspect.go)；本次判定以服务器真实导出证据为准。

修复后对已成功导入的镜像先进行上述严格校验并复用，保留原失败日志，新增 `loaded_identity_receipt_v2.json`。本轮自己的成功导入日志仅用于归属证明，镜像是否可清理由执行器再结合最初镜像基线决定；不会把失败后的404简单当成“未导入”而再次下载。原始小元数据与回执在 `runtime_preflight/docker29_identity_probe/`。
