# 官方镜像离线导入与身份核验

本记录属于 repair50 的测试环境准备，不改变抽样顺序、模型配置、提示词或评分规则。

## 为什么准备另一条传输路径

共享 Docker 的只读 `docker info` 显示 `HTTPProxy` 和 `HTTPSProxy` 均未配置。客户端 shell 中存在批准的代理，不代表 Docker daemon 会使用该代理。首题原 daemon pull 长时间只有两条 `Pulling fs layer` 记录；这与网络路径差异一致，但仅凭这些事实不能确定底层网络失败原因或宣称零字节传输。

备用方法由资格执行器在终止本轮自己的原 pull 客户端后串行使用：用户态 crane 经已批准的代理下载同一个固定摘要的公共官方镜像，先验证归档，再通过 `docker load` 导入已有 daemon。没有修改共享 daemon、启动特权容器、切换任务或跳过大镜像。

## 身份证明链

`code_repair50/image_transport.py` 采用以下校验：

1. 只接受 `swerebench/...@sha256:...`；从原公开 manifest 回执重新验证原始 manifest 摘要。
2. 不提取第三方归档路径。归档只允许一个镜像、一个 config 和原 manifest 指定的层，拒绝额外路径、非普通文件及重复成员。
3. config 的字节数和 SHA256 必须与原 manifest 一致；镜像必须是 Linux/amd64。
4. 各层压缩字节数、SHA256 及顺序必须与原 manifest 一致。流式 gzip 解压计算真实未压缩 SHA256，必须逐项等于 config 的 `rootfs.diff_ids`。
5. `docker load` 后分别识别旧版 config 摘要型 ID 和 containerd manifest 摘要型 ID。后者必须与原 manifest 的完整字节摘要，或 Docker29 描述符字段顺序重新序列化后的完整字节摘要精确一致，并与实际 `Descriptor.digest/size/mediaType` 一致；config 与各压缩层的所有描述符字段保持完全相同。`RootFS.Layers` 必须逐项等于已校验 diff IDs。正式容器使用实际核验出的不可变本地 image ID。

导入前还检查归档 `RepoTags`：若某个标签指向无法通过上述完整身份链验证的其他镜像，则拒绝导入，防止改变共享 daemon 中已有标签的指向。同一个 config 在 containerd 中显示为 manifest 型 ID，不应被错误判定为另一张镜像。无标签的归档不需要此类查询。

**归档导入不保证保留 `RepoDigests`。** 回执分别记录原 registry reference 与实际本地 image ID；不会将缺失的 RepoDigest 写成验证成功，也不会通过重新打官方摘要标签伪装这一点。

## 运行边界与回执

- 每次只进行一条完整下载路径。首题小 manifest 连通性核验实测 3.83 秒成功，没有下载任何镜像层；这一结果不等于完整镜像或正式测试已成功。
- 下载与导入期间每秒检查共享镜像所在盘剩余至少 10GiB、`/tmp` 至少 20GiB；触及门槛或预设超时仅终止本轮自己的客户端。
- 不启动容器，不调用模型，不修改 daemon 配置，不 prune 或删除其他镜像。资格执行器单独管理本轮镜像租约和容器。
- 首次完整下载、压缩和未压缩哈希核验、导入日志与本地身份回执分别保存。已验证的镜像仍存在时直接复用；本轮清理后可从同一归档重新导入，重新导入日志采用独立目录，保留原回执。
- 候选资格仍必须由正式 gold/base 测试确定。镜像传输故障属于系统阻塞，不能按镜像大小替换候选，更不能将其计作模型修复失败。

入口为 `ensure_verified_image(client, manifest_record, workdir=...)`，由资格执行器单路调用。相关 CPU 单元测试检查摘要篡改、层顺序、真实解压 diff ID、额外归档路径、缺失 RepoDigest、匿名凭据隔离及缓存复用；这些测试不代替真实镜像导入和正式测试。

## 有限 Range 吞吐探针

在首镜像原 crane 下载继续进行期间，对同一个公开层进行了不超过 16MiB 的小探针。请求全部返回严格正确的 HTTP206、Content-Range 和字节数。

| 小探针 | 有效载荷 | 耗时 | 吞吐 |
|---|---:|---:|---:|
| 四个 1MiB 段，单连接依次请求 | 4MiB | 17.59秒 | 0.227MiB/s |
| 四个 1MiB 段，四连接并行 | 4MiB | 5.69秒 | 0.703MiB/s |
| 四个约 1.984MiB 段，四连接并行 | 约7.94MiB | 6.46秒 | 1.229MiB/s |

探针累计有效载荷 16,711,680 字节，小于 16MiB。小段并行比同样小段串行快，但请求建立延迟占比很大，不能据此宣称整个镜像会获得同样倍数的提升。较大段探针的绝对吞吐没有明显超过同期持续 crane 下载的观察值，且探针与原下载共用网络，不能当作严格独立吞吐基准。

因此没有启动第二条完整镜像下载，也没有把并行 Range 下载加入正式执行路径。继续使用已核验的 crane 方案。原始探针回执为 `runtime_preflight/range_transport_probe.json` 和 `runtime_preflight/range_transport_probe_larger_segments.json`。

## OCI gzip 官方镜像兼容

前4题资格通过后，第5候选 GitPython-2051 在任何完整下载或测试执行前被旧媒体类型白名单拒绝。其原镜像实际为 OCI v1 manifest/config，7层均是 OCI gzip，并非 zstd；原摘要为 `sha256:77292204f8b9bd53d60e5f24789834207877c1d4662d7226da2bf4bb2f7f32ae`。这是传输程序格式兼容问题，不能作为替换候选的理由。

在已发布恢复点 `650ca598b41ebde2b45deda59e5e529c1161d364` 后，白名单增加了 OCI manifest、config 与 gzip 层。原 manifest、config、压缩层字节和所有摘要均保留。OCI 官方规范将 [OCI gzip 与 Docker gzip 列为兼容媒体类型](https://github.com/opencontainers/image-spec/blob/v1.1.1/media-types.md#applicationvndociimagelayerv1targzip)，故仍使用同一 gzip 解码器逐层校验实际 diff ID，没有安装新的解压依赖。

Docker tar 格式只记录 config 与层路径，可能在导入时重建 Docker 类型的 manifest。因此预定义了只改变三类 MIME 表示的严格候选：OCI manifest/config/gzip分别映射为对应 Docker manifest/config/gzip；不得更改任何 config或层的摘要、字节数与顺序。只有该候选的**完整 SHA256**精确等于实际 image ID，并与 `Descriptor.digest/size/mediaType` 一致，才接受该表示。原 OCI 摘要继续单独保存，绝不声称原 RepoDigest 必然保留。

回执通过 `runtime_descriptor_media_types_translated` 显式披露是否发生 MIME 表示映射；`same_original_config_and_compressed_blob_digests_and_sizes` 记录内容摘要和大小保持一致。发生 MIME 映射时，不能再把所有描述符字段写成完全相同。

本次 CPU 验证共202项通过，其中传输模块25项，覆盖原生 OCI ID、Docker MIME 映射、错误层摘要拒绝、原 manifest 不被修改及未知压缩类型拒绝。随后第5题真实导入所得 ID `sha256:8cc3262f7df6a6011c8f8f08372672350c9187e449b420e500eb93b0184f0d04` 精确匹配预定义 MIME 映射候选；正式 gold 成功、empty 未解决且观察到1个实际 FAIL_TO_PASS 失败，资格通过。证据为该候选 `infrastructure_attempt_2/qualification.json`；不能只凭离线格式测试给其他题资格。

## 保留失败现场的同摘要恢复

ReCirq-410 的第一次公开镜像传输在最后117字节层处遇到 GET EOF。只读诊断确认：旧 tar 为2,635,010,048字节；config 10,883字节和前6个压缩层共2,634,993,138字节全部与原 manifest 的SHA和大小一致，仅缺末层及 Docker tar 的 `manifest.json`。诊断包含整份 partial SHA和原始日志SHA，位于 `runtime_preflight/recirq410_partial_archive_diagnostic.json`。这不是模型失败或正式测试失败，旧 tar 不能直接导入。

在已发布恢复点 `ef9d4afc6f18fc9f15d8b5f8efc82294a053a2de` 后，加入显式调用的 `recover_verified_partial_image(...)`：

1. 原 partial 和失败日志保留原路径；创建唯一独立 `recovery_attempt_1`，已经存在的尝试不覆盖、不自动再次执行。
2. 原 manifest 摘要先验证。仅将旧 tar 中大小、完整压缩SHA均匹配的原始层字节写入新的私有cache，以临时文件和原子rename发布；不信任文件名、不提取第三方路径。
3. 仅允许合计不超过16MiB的缺失blob。预留私有cache、新完整tar与20GiB磁盘余量，复制过程中继续检查空间；恢复失败则保留回执并停止。
4. 使用同一官方固定版本 crane、同一个 `@digest`、同一平台和Docker tar格式，只增加官方 `--cache_path`。这使已核验层能从本地读取，不需要重新下载大层。manifest/config等小元数据仍按官方流程读取。
5. 新tar再次通过原有全部压缩SHA、实际解压diffIDs和导入后身份门。只有成功回执与原source reference和digest严格相符，后续 `ensure_verified_image` 才能转到新的完整归档目录；失败回执不能触发回退全量重拉。

cache遵从[固定版本官方格式](https://github.com/google/go-containerregistry/blob/v0.22.1/pkg/v1/cache/fs.go)，不新增下载器，不改变样本或测试协议。这是基础设施传输恢复，不重试模型补丁或根据模型成绩换题。原始资格与模型执行仍由各自执行器控制，恢复helper不会启动资格测试或模型。

## 严格小尾层EOF的自动单次恢复

`ensure_verified_image` 现在仅捕获带阶段和类别的 `CraneDownloadError`。原crane非零退出时，先持久保存原始失败回执，记录日志SHA、partial大小与mtime、原source/digest及退出码。只有正常退出码1，且最后一行精确为同一原manifest中blob的HTTPS GET EOF，才继续检查恢复资格。允许官方Docker Hub的 `index.docker.io` 和 `registry-1.docker.io`；其他host、HTTP错误、主动终止、超时、权限、磁盘、校验错误均不按EOF恢复。

恢复还要求目录名等于原digest、目录是当前用户私有700目录、相关文件为当前用户持有的普通非符号链接文件、原日志及partial自失败后未变、source与本地原manifest回执严格相同、此前没有 `recovery_attempt_1`。crane子进程单独使用umask077创建后续归档，不修改主进程或宿主机的umask。只有只读重算已有完整blob的SHA之后确认缺失blob合计不超过16MiB，并满足原磁盘预留，才调用既有独立恢复helper一次。

恢复不会捕获一般身份、磁盘、权限或超时异常。不会在模型或测试失败时触发，也不会对恢复失败循环重试。原失败、资格检查决定和唯一恢复attempt分别留证；失败继续作为系统阻塞，不能替换候选或计成模型修复失败。后续完整归档、实际diffIDs、导入身份和归属门全部照常执行。第8题的大层长连接停滞不满足这条小尾层EOF规则，此批未为其放宽16MiB上限或增加跨归档缓存。
