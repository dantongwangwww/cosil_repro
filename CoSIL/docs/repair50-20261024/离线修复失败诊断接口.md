# 离线修复失败诊断接口

`code_repair50.case_analysis` 只读本轮已落盘产物，不调用模型、不执行仓库、不读取参考修复或隐藏测试源码。按同一 instance_id 拼接正式名单、每组唯一候选记录与源码可见性审计；不会挑选成功版本或重试失败题。

```python
from code_repair50.case_analysis import build_case_report

build_case_report(
    roster,                 # {frozen: bool, tasks: [...]}
    arm_records,            # 每个 instance_id × A/B 最多一条汇总
    context_audits,         # 现有 prepare_case 生成的 context_audit
    artifact_root=run_dir,  # 必须覆盖两组已有补丁和正式评测文件
    output_dir=new_report_dir,
)
```

输出：`修复失败分析_先分类再逐题.md`、`修复失败逐题诊断.csv`、`修复失败诊断.json`。目录中的旧文件若内容不同则拒绝覆盖，适合随不可变报告快照生成。

读取文件名限于模型 `patch.diff`、`evaluation_record.json`、`result.json`、`official_report.json`、`parsed_test_statuses.json`；拒绝越界路径与符号链接。模型 diff 仅解析修改文件身份。正式测试状态仅用于失败数量和观测完整性，不将测试正文、参考答案或失败反馈传给任何模型。

分类先列同题结果，再列两组失败阶段，最后逐题说明；仅B成功与两组正式未解决优先展示。解析失败、应用失败、评分完整性拒绝、截断、环境故障、预算未执行、未知原因分别保留。F2P/P2P同时展示官方判分失败数量和实际观测失败数量：缺失测试可能被官方判失败，但不能据此断言已经实际运行并失败。

仅B成功且伴随B新增目标源码只说明关联；同源码时也不能排除采样波动。只有 expected 全观测且正式未解决时，才写“测试要求未满足”。是否遗漏联动修改或具体逻辑缺陷没有充分证据时保留原因不确定，不根据与参考补丁的差异判错，不把两组都失败直接解释为代码生成能力不足。
