## 二、pruner 剪枝机制总结（基于全部 107 条判决+影子）

1. **准则是文本相似度，供词一致**：影子理由绝大多数以"文本相似/命名匹配/不匹配"开头；11001-shuffled 对 get_order_by 判 True 的影子原话："函数名 get_order_by 与报告相似，因此判定相关"。
2. **判决不可复现**：同一函数同一 issue，11848 的 parse_http_date 三臂两判（True/False）；与 v2 实验一的 11400 翻转互相印证。
3. **新版子 agent pruner 更狠但更瞎**：判 False 占多数（off 12F/5T、on 33F/10T）——它砍掉了大量语义不像的候选（包括砍掉过 gold 本尊 11848-on），但砍的依据仍是长相。
4. **因果词汇 ≠ 因果判据**：12470 的影子会说"体现因果作用"，但判的对象是无辜的 Options.\_\_init\_\_。

## 三、"注释为什么没发挥作用"——五种机制（每题对号）

| 机制 | 对应题 | 一句话 |
|---|---|---|
| ① 早退压倒一切 | 12907×3、14365×3、11001-off、13031-off/sh、11400-sh | issue 点名太醒目，注释菜单在场也拦不住秒答（14365 的盲答改善是唯一例外） |
| ② 无效激活 | 6938-on、13031-on、13895-on、11400-on | 注释让模型翻得更勤（事件数翻倍），但翻的全是症状家族——**给了干劲，没给方向** |
| ③ 看见但不选 | 11001-on/sh | gold 类代码进了上下文，最终排序仍被 get_order_by 压住（选择层病，实验二已证） |
| ④ 判决随机性盖过处理效应 | 11848 三臂 | 同一 gold 函数 pruner 两判；注释的影响小于 pruner 自身方差 |
| ⑤ 门槛外无解 | 10914、12470、11400、13895 | 文件级 top-5 不含 gold 文件，函数级做什么都白搭 |

**净结论**：注释的两点真实效果——(a) 微弱提高盲答质量（14365）；(b) 显著提高探索意愿（事件数翻倍）——都不触碰主瓶颈（早退、症状锚定方向、文件级门槛）。而它可能的负面（错位注释污染参数格式、让无效探索更有耐心）也在日志里留下了痕迹。
