## getmoto__moto-9350：查询结果症状，修改点在创建对象时保存路由表

Issue 报告 `DescribeTransitGatewayAttachments` 返回固定的示例路由表 ID，而实际关联的路由表不同。补丁让 attachment 构造函数接收 transit gateway 对象，并保存其 `default_route_table`；VPN、VPC、peering 创建方法相应传入对象。响应模板随后使用对象中的路由表 ID，并处理没有路由表的情况。

6 个既有函数目标都在 `moto/ec2/models/transit_gateway_attachments.py`：`TransitGatewayAttachment.__init__`、`TransitGatewayPeeringAttachment.__init__`、`TransitGatewayVpcAttachment.__init__`，以及 `TransitGatewayAttachmentBackend` 的三个 `create_transit_gateway_*_attachment` 方法。响应模板属于模块级内容，不增加函数目标。

该模型文件在文件选择结果中排第 2，完整源码进入最终请求，6 个目标定义均完整覆盖。模型返回 6 个有效函数身份：前两项是 response/model 两层的 `describe_transit_gateway_attachments`，后续是 attachment/route-table 的 association 方法。6 个构造或创建目标均未进入返回列表。证据支持“目标源码已经到达，但最终选择落在查询和关联接口”，本例无需以检索缺失解释。

## iris-hep__func_adl-199：目标文件已到达，输出选择另一转换阶段且身份非法

Issue 的条件字典展开表达式在 AST 类型推导时触发分支类型不一致。补丁在 `func_adl/ast/syntatic_sugar.py::resolve_syntatic_sugar` 内添加字典合并和 `visit_Dict` 处理：展开字典、求解常量条件的 `IfExp`，并对不能静态求解的条件给出错误。新增的内部辅助方法按范围规则另记；既有外层 `resolve_syntatic_sugar` 是可定位目标。

`syntatic_sugar.py` 在文件选择中排第 2，文件 1–205 行完整进入最终上下文。模型的 3 个输出却全部位于 `func_adl/type_based_replacement.py`，分别为 `visit_IfExp`、`visit_Dict`、`lookup_type`，限定名均带 `remap_by_types.<locals>.type_transformer...`。JSON 本身合法，但这 3 个身份不能按冻结的 AST 身份规则匹配，因此保留三个无效槽位。

本例同时存在“选择了另一文件/转换阶段”和“限定名不符合可执行身份规则”两项可观察事实。即便删除 `<locals>` 字样，这 3 项仍不等于补丁目标 `resolve_syntatic_sugar`，不能把全部失分归结为 JSON 语法问题。

## aws-cloudformation__cfn-python-lint-4368：命中规则入口，漏掉底层额外属性检查

Issue 是合法的 `Fn::Transform` 放在 `AWS::CloudFormation::Init` 中时触发 E3009。补丁在 `src/cfnlint/jsonschema/_utils.py::find_additional_properties` 中导入并识别 `FUNCTION_TRANSFORM`：当当前 validator 上下文允许该函数时，将其从额外属性检查中跳过。

文件阶段最终只保留 `src/cfnlint/rules/resources/CfnInit.py`；函数阶段只输出 `CfnInit.validate`。实际目标 `_utils.py` 没有出现在传给文件选择阶段的文件清单中，后续 grep 也没有恢复目标定义的任何交叠区间。最终请求成功，但没有携带目标函数体。

该输出定位到了 Init 校验规则入口，补丁则修复共享的 JSON Schema 属性检查。日志支持的直接限制是目标工具函数未到达最终上下文，不能据此判定模型已经读过该实现后仍拒绝选择它。

## bodo-ai__PyDough-368：方法体定位正确，所属类身份不匹配

Issue 涉及 BEST 在祖先上下文或全局上下文下的 singular/cardinality 处理。补丁新增 `PyDoughCollectionQDAG.is_ancestor`，并在既有 `pydough/unqualified/qualification.py::Qualifier.qualify_best` 中改用祖先关系判断，对 GLOBAL BEST 也构造 singular 结果。新增 helper 属于范围外新增函数；既有 `Qualifier.qualify_best` 是本题唯一函数目标。

`qualification.py` 没有进入最终整文件选择，但 grep 恢复了 1144–1221 行的完整目标方法体。最终上下文块的标题只有路径、行段和 `evidence span`；全部发送源码中没有 `class Qualifier` 声明。

模型首项给出相同路径、相同行段以及 `qualify_best` 方法名，但限定名写成 `Qualification.qualify_best`，与 base 中的 `Qualifier.qualify_best` 不同，因此首槽按冻结身份规则无效。其余 3 项是 `Singular.is_singular`、`PartitionBy.is_singular`、`HybridTree.is_singular`，均不属于本题 gold。

本例表明源码块已提供正确方法体，但未提供所属类声明；结果中的类名前缀不匹配足以导致严格函数级未命中。将它概括为“目标源码没有到达”或“完全没找到目标方法”都会掩盖这一实际边界。

## pymc-devs__pytensor-1701：新增 scalar 方法与删除既有方法须分开评价

Issue 文本列出 scalar 反向除法及 `InRange` 初始化问题，并给出建议修改。实际业务补丁在 `pytensor/scalar/basic.py` 新增 `__rtruediv__`、`__rfloordiv__`，还删除两个文件中的过时除法方法；最终 gold 必须以实际补丁及 base 定义为准。

新增 scalar 方法在 base 中不存在，记为范围外新增函数。4 个被删除的 base 既有函数仍是本题可定位目标：`pytensor/tensor/variable.py::_tensor_py_operators.__div__`、`_tensor_py_operators.__rdiv__`，以及 `pytensor/xtensor/type.py::XTensorVariable.__div__`、`XTensorVariable.__rdiv__`。删除既有函数不会使目标变成 NA。

5 次文件选择都只返回 `pytensor/scalar/basic.py`。模型最终输出该文件中的 `_scalar_py_operators.__truediv__`、`InRange.__init__`、`ScalarOp.__init__`，其中 `InRange.__init__` 在冻结 base 身份检查中无效。`tensor/variable.py` 虽有 176–177 行 grep 片段，但与两个被删方法的定义区间不交叠；xtensor 目标也没有到达。

可观察的偏差是返回列表围绕 issue 中 scalar/operator/初始化描述展开，而实际补丁的 4 个既有删除目标分布在另外两个文件，均未被源码检索恢复。这里不能把新增方法无法定位，混同为删除目标不可评价。

## home-assistant__core-134506：旧 NA 恢复为可评分，预测仍是另一类的同名方法

Issue 报告新实例尚无 backups 目录时上传备份失败，手动创建目录后可成功。补丁在 `homeassistant/components/backup/manager.py::CoreBackupReaderWriter.async_receive_backup` 中、移动上传的临时文件之前，通过 executor 创建目标父目录。

旧 v1 的 Python 3.11 索引器在该文件已有的新语法 f-string 处解析失败，导致整文件没有定义；Python 3.12 离线索引恢复了这个唯一既有目标。该修正只改变本次离线金标，旧预测和旧评分没有改写。

模型的文件选择为 `http.py`、`config.py`、`backup_restore.py`；`manager.py` 未进入文件清单和最终整文件选择。grep 取到了 `manager.py` 189–249 行的 `BackupManager.async_receive_backup`，但未覆盖文件后部实际修改的 `CoreBackupReaderWriter.async_receive_backup`。模型首项正是 `BackupManager.async_receive_backup`，第二项为 `UploadBackupView.post`，第三项身份无效。

本例有两个独立事实：评测侧原先因解析兼容性而 NA；恢复完整金标后，原预测选中了另一类的同名上传方法，且真实目标方法体未进入最终请求。

## beeware__briefcase-2241：安装失败的修复在项目配置模板

本题原 v1 已是 fully_mappable。Issue 是 macOS/Python 3.13 创建 PySide6 应用时，所声明的 macOS 11 最低版本使新的 PySide wheel 不兼容。补丁在 PySide bootstrap 的 pyproject 模板中声明 `min_os_version = "12.0"`，更新 PySide 版本及相关依赖。

3 个既有目标是 automation bootstrap 的 `PySide6AutomationBootstrap.pyproject_table_macOS`，以及正式 bootstrap 的 `PySide6GuiBootstrap.pyproject_table_briefcase_app_extra_content`、`PySide6GuiBootstrap.pyproject_table_macOS`，分别位于 `automation/src/automation/bootstraps/pyside6.py` 和 `src/briefcase/bootstraps/pyside6.py`。

模型最终选中 macOS/iOS/create/subprocess 等安装流程文件，bootstrap 文件未进入最终整文件上下文，grep 也未恢复 3 个目标定义。前 5 个输出为 `macOSCreateMixin._install_app_requirements`、`CreateCommand._pip_install`、`CreateCommand._install_app_requirements`、`CreateCommand.install_app_requirements`、`iOSXcodeCreateCommand._install_app_requirements`；后 3 项仍是 pip 参数/依赖处理函数。它们是有效身份，但均不属于补丁的配置生成函数。

证据支持“选择安装执行流程、遗漏生成最低系统版本与依赖配置的模板方法”。不能把错误归因于完整模板源码到达后的函数排序，因为这些目标定义没有到达。

## UXARRAY__uxarray-1369：切片异常的修复在前置索引校验

本题原 v1 已是 fully_mappable。Issue 中 `var[0]` 对非网格维度索引时，为网格维度保留的 `slice(None, None, None)` 被错误当作实际网格切片，进入 `_slice_face_indices` 并触发类型转换异常。补丁修改 `uxarray/core/utils.py::_validate_indexers`：识别完整的空边界 slice，并在计算需要实际处理的 grid dimensions 时排除它们。

文件选择和最终返回均围绕 `uxarray/grid/slice.py`、`uxarray/core/dataarray.py`、`uxarray/grid/grid.py`。3 个输出依次是 `UxDataArray.isel`、`_slice_face_indices`、`Grid.isel`。目标 `core/utils.py` 没有入选，grep 也没有给出目标定义的交叠区间。

模型选择了异常出现的切片与分派调用链；实际补丁把无操作 slice 从前置 indexer 分类中剔除。可观察的直接限制是该前置校验函数未到达最终请求。
