# 独立函数评价 v2

本批实现前检查点为 `dfab02c2d7cf595807c9cfed735174dbaca91e71`。实现位于 `dsimple_v2/gold.py`，只使用标准库，在独立 CPU 进程中处理生产补丁与基础源码；不导入模型、provider、在线工具或旧报告 main，不执行补丁后的代码、修复测试或封存 test。旧 gold、预测、在线 Python3.11 索引不改。

当前逻辑工程目录整体软链接到 `/tmp` 工作区，不是永久交付。永久代码发布、报告与证据归档由 root 统一完成。

## 对象与主分母

v2 评价**生产补丁触及的、base 中已存在的具名 Python 函数身份**，不是修复成功率，也不是因果根因真值。精确身份仍为 `base路径::base限定名`；保留嵌套函数、async、类方法。同QN的property getter/setter和overload共享评分ID，但各span分别留证据，不因span不唯一而丢身份。

主表条件：`status == COMPLETE_NONEMPTY`，即既有函数目标非空且该集合提取完整。

| 状态 | 含义 |
|---|---|
| COMPLETE_NONEMPTY | 完整取得至少一个有效既有函数目标，进入主表，定位运行失败保留分母 |
| COMPLETE_EMPTY | 已证明本政策范围内没有既有函数目标；保留模块/类/新增符号/非Python等NA原因 |
| INCOMPLETE | 补丁、源码、AST或函数对应有未解决错误；已知目标只能作辅助，不能冒充完整集合 |

模块、类、import、空白、注释、新函数、新文件可与既有函数修复共存，不再单独排除整题。因此主表Recall/AllCoverage是“既有函数目标集合”的覆盖，不能称整补丁所有修复目标的覆盖。v1状态、原目标集合与v1→v2增删身份逐题保留。

## 实际算法

1. 从clean job确定base snapshot、路径和旧索引。遍历旧索引全部路径及job全部`.py`路径，用tokenize规则解码，记录raw/text SHA，核对旧索引text SHA。这个模块核验的是冻结索引所记录的源码文本；不宣称重新执行Git checkout或独立复核上游qualification的全部raw字节证明。
2. 将源码送至已安装的 `/usr/bin/python3.12 -I -S` 标准库AST子进程；记录精确解析器版本和worker代码SHA。所有base文件重新生成v2索引，避免只处理gold路径而把其他有效预测错判无效。未涉及补丁的文件即便AST失败，也明确保留parse_error路径，供评分器识别证据缺口；不能假装成功空索引。
3. 解析Git unified diff，校验hunk两侧行数、上下文、删除文本、坐标和无尾换行标记，在内存应用。保留未改动行的`new→old`坐标对应。不把hunk标题或context行当实际改动。
4. 对每个涉及文本hunk的既有主Python文件，base/fixed必须完整可解析且补丁、源码完整性核验通过。任何该类错误使整题INCOMPLETE，绝不使用`except: defs=[]`再判空gold。
5. 增删行取AST中最内层具名function owner，span从最早decorator至end_lineno。删除行直接加入其base函数身份。增加行优先按未改动def行确定旧函数，必要时用未改动、直接属于该函数的body行确定唯一旧owner；多个旧owner候选记未解决对应并使INCOMPLETE。
6. 新owner无法证明延续旧span，但精确QN在base存在时，遵循共享ID政策加入该既有身份，证据为`new_definition_existing_identity`且`matched_base_span=null`。典型情况是新增setter/overload。它不证明新增实现原本在base可见；实际修改span覆盖须另报。
7. 新QN无base身份且无旧函数延续证明，记`new_or_renamed_function_without_base_identity`，不加入主目标；函数rename的删除侧仍会保留旧身份。无function owner的行按blank/comment/class/module分类，不强塞给最近函数。
8. 每个实际增删行都进入映射证据或scope-exempt证据；异常单列。输出case级JSON与全部base文件v2 AST索引，绝不改旧文件。

函数内docstring/注释仍按patch所属函数映射，不偷偷变为“只计可执行语句”的新政策。现模块不自动判定docstring-only因果修复；例如smart_open的open仅文档改动仍须在报告单独披露，不能当作已定位真实seek实现。

## 特殊边界

- 函数rename使用base旧名；类rename且方法同时改动时，通过未改动def/body行归回base旧类QN。纯类名、继承或类decorator改动不自动把全部方法拉入gold。
- 文件rename/move带函数内容改动时用base旧路径；纯路径/模式变化没有函数源码改动，函数集合可以为空。无普通hunk的Git rename元数据单独支持。
- 新文件没有base函数目标，记`new_file_no_base_functions`；本模块不声称统计了新文件内全部新函数。
- 删除函数/方法/整个文件仍可通过base删除行取得目标；fixed为空是正常状态。
- 仅新增nested helper时，按最内层owner记新函数，不临时上移到外层函数；若外层调用语句也改，外层会正常成为目标。
- lambda没有具名FunctionDef身份：类/模块内lambda是范围边界，具名函数内lambda仍属于该外层函数。
- 既定主Python排除政策与原方案一致：测试/文档路径和非`.py`文件另记scope-exempt。公开Lite的test split不等于封存pruner test；本模块拒绝读取holdout/split_manifest/pruner_test路径。
- 损坏或不支持的生产补丁、缺失base、SHA不符、hunk不一致、Python3.12仍不支持的相关源码、无法裁决的函数对应均明确INCOMPLETE。非Python/全新文件排除不是解析错误兜底。

## 接口、产物与复现

Python接口：

```python
evaluate_case(job_path, benchmark_row_path, output_dir, v1_gold_path=None)
```

`benchmark_row_path`应指离线投影的`instance_id/repo/base_commit/problem_statement/patch`五字段JSON；不提供test_patch/harness列。输出目录必须位于新ROOT的`evaluator_private/eval_v2`内部。

CLI：

```bash
PYTHONDONTWRITEBYTECODE=1 /mnt/skygruop0/home/wdt/cosil_repro/CoSIL/.venv-v5/bin/python -m dsimple_v2.gold \
  --manifest manifests/external100.json --cohort external100
```

descriptor含`records`，每条使用canonical字段`instance_id/job/private_row/v1_gold/origin/result_dir`；提取器读取前四项，origin用于汇总，result_dir由报告层只读取预测。Lite旧55可使用`manifests/lite_reuse55.json --cohort lite270`，其mapping_summary此时只代表55条已输入记录，不能冒称270题完整状态；新215准备后用最终完整manifest统一汇总。

每题输出`{gold_v2.json,code_index_v2.json,evidence/file-NNNN.json}`。gold字段包括`status/existing_function_target_set_complete/existing_function_targets/gold_files/changed_line_evidence/scope_exempt_changes/file_evidence/errors/parser/code_index_v2_path`，以及v1对照。`gold_functions`是existing_function_targets的兼容别名。

`code_index_v2.json`沿用原file_record结构：`path/sha256/lines/definitions/parse_error`，另加raw_sha256与parser_version；definition含qualified_name/start_line/end_line/kind/def_line。独立评分器统一用此索引验证所有方法raw预测，保留重复、None和无效槽，P@k固定除k，不用叶名或祖先宽松追回命中。

cohort级`mapping_summary.json`给分配数、三状态数、v1分布、每题目标数和身份变化；单case evidence保留精确old/new行图和span证明。所有带gold的输出均为离线私有产物，推理namespace不可见。

## 评价修订 r2：唯一完整上下文的精确偏移

实际old/new起点、offset、完整旧块行数和proof写入`file_evidence.hunk_placements`及逐文件evidence。新行号和new→old映射由实际应用位置重建，不能继续用陈旧的hunk header坐标映射函数。每条placement都显式`fuzz=false`。无法唯一定位仍为INCOMPLETE。
